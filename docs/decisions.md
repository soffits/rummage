# Decisions

## Scope

- rummage is a small memory add-on for an agent: it reads sources into an index, finds passages by meaning and exact words, opens them with their context, and says plainly what its output leaves out. Judgment stays with the agent: which query to try next, what a time phrase means, whether two notes disagree, who someone is. A tool that guesses at those hides its guesses inside ranked output, where the agent can't see or overrule them, so they cost more than they give.
- So these are not in rummage: `dupes`, `conflicts` and `about` (an agent finds a person's mentions with `search --sort newest` and judges duplicates and contradictions itself); reading time phrases in queries (the agent turns "last Wednesday" into `--since/--until`); `next_actions` that suggest a strategy (only facts stay: masked values, a partially indexed item, an empty index); `--truncate` (the agent reads the scores and `summary.strong`); recall's refer-back phrase list (recent turns come in only when they share words with the prompt); `serve`, remotes, tokens, the container image and a Postgres design (an index lives with its agent, and other machines' data is read through their APIs); `rummage mcp` (agents run the CLI); the generic `jsonl-chat` source (each harness gets its own source type, which knows its format).

## Model and runtime

- EmbeddingGemma 2, first 512 of 768 dimensions, float16 storage, as the default: near-lossless on MTEB, a third less storage and compute.
- Models are profiles (files or endpoint, prompts, dimensions, thresholds), not constants: benchmarks put most of the quality in the model, so a better one has to drop in with a config line. Sources store the model-independent input `(title, text)` and each profile writes its own prompt around it, so a switch re-embeds without reading sources again.
- A switch builds the new vectors beside the old ones in the same index (a `vectors` table keyed by model) and swaps in one transaction, as Qdrant's blue-green migration does with two collections and Smart Connections v3 with per-model embeddings; a second index file would need its own reading of every source and a merge of what changed meanwhile. Old vectors stay until pruned, so a rollback is instant. Khoj re-embeds in place and Continue keeps a table per provider without a swap step; both leave search on a half-built index meanwhile.
- The switch is a record in the index moved along by ordinary embedding runs, not a separate job: `watch`, the hourly run and a manual `rummage index` all advance it, and it resumes from committed batches after a kill.
- Thresholds are calibrated per model by quantile matching against the model being replaced, on the user's own index (probe queries cut from sampled passages, scored against other items): no labelled data needed, and a model compared with itself gets its own thresholds back. Khoj keeps a hand-set threshold per model instead. The share-based target for an index with no previous model was measured with EmbeddingGemma 2 on BEIR SciFact, because the live index and SciFact agreed on the gates (2.3% vs 2.6% at z 2) but not on near-duplicates.
- The comparison before a swap is known-item search with the same probes: it needs no judgements, runs on any index, and catches a model that can't find what the old one found; the public set (SciFact) is on request because it takes minutes of embedding.
- A remote endpoint is either a profile's own model (`url`) or an accelerator for a local profile (`[embedder] url`), trusted only when its reference vectors agree; an OpenAI-compatible request (`input`, optional `model`, bearer key) covers llama-server, vLLM, TEI and hosted APIs. Without `/tokenize`, long inputs are split by size (two bytes per token at least).
- llama.cpp `llama-server` with ggml-org's Q8_0 GGUF: one runtime for text and images, official prebuilt CPU builds, the same files DigUp checked against the reference. ONNX int8 was ~25% faster on text but needs our own image preprocessing.
- The server runs as a child for one run on 127.0.0.1 and a free port; the only resident process is the query daemon.
- Passages are cut by characters (~1800), but the server's limit is tokens, which no character count bounds (a byte-fallback tokenizer spends a token per byte on invisible and rare characters). So the embedder owns the limit: it measures any text that could exceed a micro-batch with the server's tokenizer, embeds it in halves until each fits, and averages the vectors by token count. One passage stays one vector, and no source has to know the tokenizer.

## Index and ranking

- One SQLite file: items, segments with their model input, vectors per model, contentless FTS5, per-source cursors, run history. An index from before profiles is migrated in place when opened (vectors move to the new table under the old version); its passages' inputs weren't kept, so a later switch reads those items again.
- Ranking adapted from DigUp: z-scored cosine per modality, z ≥ the model's gate (2 for EmbeddingGemma 2) counts as a meaning match, word coverage bonus, ID and number queries weigh words double.
- CJK characters (Han, kana, Hangul) are single FTS tokens and CJK query runs become overlapping character pairs, so two-character words match in any CJK language and Korean particles don't block a match; trigram tokenizers can't match two-character words.
- Brute-force numpy scoring instead of an ANN index or sqlite-vec: fast enough for a few hundred thousand vectors, no alpha dependency.

- One z-score scale per modality, not per script: scaling CJK passages separately cut their drift into unrelated CJK queries only slightly and pushed a CJK answer down for a CJK question on a mostly English corpus. Measured again with the script stored per passage: per-script centring lifted answers in another script for CJK questions but pushed them down for Latin questions and pushed same-script answers down, so it stays per modality.
- The word bonus is weighed by the share of meaning matches (z at or above the gate) written in the query's script: exact words can only be found in that script, so when most plausible matches are in another one, meaning decides. ID and number queries keep the full weight. A passage's script (`text.script`: CJK as one family, else the Unicode script of its letters) is stored with the segment and filled in on open for segments that have none.
- Recency is an additive bonus over the plausible matches (`RECENCY_WEIGHT` for the newest, halving every `RECENCY_HALF_LIFE`), as in Generative Agents' recency decay and time-decayed hybrid search, rather than newest-first order: a weak new match must not jump a clearly better old one. Age counts from the newest candidate, not from now, so an old archive still ranks its newest items first. An item's time is a message's own time, else the file's modification time.

## Progress

- Indexing progress lives in `progress.json` in the data folder, one part per kind of run (`read`, `embed`), each
  rewritten atomically at most once a second. Status bars, prompt hooks and search output read that file and never
  query the index for it, so they can ask every few seconds; a run recounts the passages still waiting every 10 s
  and readers subtract what it made since.
- A read samples its own pace and the time left is the longer of the items still to read at that pace and the vectors still to make at theirs. The read's pace is items over the last half hour up to the moment of asking, the count at the window's start interpolated between samples the run writes down every 30 s, so the time since the last finished item counts and the guess moves smoothly; it says "unknown" until the read has run five minutes and read 20 items. Items differ far more than passages (a picture whose OCR is cached takes a second, a long scan many minutes), and a five-minute pace swung from "9 min" to "2.3 h" within five minutes when cached items gave way to scans.
- A part counts as running while its process lives and has written within 10 minutes. On Windows the process is
  looked up with `OpenProcess`, since `os.kill(pid, 0)` there sends Ctrl+C.
- Agents hear about the index only while the model searches use is missing vectors or items are still being read; a
  model switch is shown to people only, because searches keep using the old model's complete vectors meanwhile.
- Status text is ASCII, so a status line printed through a Windows code page can't fail. `status --watch` redraws in
  place only on a terminal that takes VT sequences (switched on with `SetConsoleMode` on Windows) and otherwise prints
  the table again when it changes. No library for it (rich and the like): the core stays numpy and pypdf.

## Sources

- Source types are entry points in the `rummage.sources` group, so services are plugins and third parties can add their own; the core keeps only generic folder sources.
- Bundled plugins live in `rummage.plugins.*` with extras for their packages, rather than separate distributions: one install, while the core never imports them.
- `dsh-sessions` reads who wrote a message from `source.principal` first (DSH's field for the caller behind a user message, filled by dsh-oidc and dsh-telegram-bot as `{kind, channel, id, name?}`), then from the text tag or OIDC notice: structured data beats parsing, and old logs have only the text.
- `dsh-sessions` leaves out what agents send (principal kinds `dsh-session`, `cron-job`, `external`, the old `prompt_session` line) and the replies to it, so a brief never reads as the person's words. Briefs from before the bridge recorded its sender have no sender at all; `web_senders_since` dates when every real Web prompt began carrying one, a fact about the home's login rather than a guess from the text.
- Once every channel records its sender as `source.principal` (the channel metadata contract of dsh-message-context), `principals_since` dates that and the principal alone decides; the text tags, sender notices, skip prefixes and `web_senders_since` stay only for history before it, in this one reader. Other readers of the same logs (a live recall hook, a home's message reader) read only the principal.
- Chats: one item per message a person wrote plus the reply after it; the model reads the start of both, keyword search the full text.
- Seafile: an account token with read-only shares, or a library's own API token (`/api/v2.1/via-repo-token/`) where no account is shared, or both in one source; item keys are `library id:path` either way, so switching tokens re-embeds nothing. A library is skipped while its head is unchanged (the head commit for an account; for a repo token, whose API has no commit, the root folder's id, a hash over the whole tree), then file object ids decide; archives are listed over HTTP range requests. Repo-token download links are good for one request (`FILESERVER_TOKEN_ONCE_ONLY`), so every range request asks for a fresh link.
- Size limits stay, with defaults sized for a laptop, but each is a source setting and each cut is stored on the item at index time (`info.partial`: what, kept, total, unit, setting), the way Elasticsearch records ignored fields in a document's [`_ignored`](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/mapping-ignored-field) and Apache Tika marks a [write limit reached](https://tika.apache.org/docs/4.2.x/advanced/setting-limits.html) in the extracted metadata; a debug flag that lists skipped files, as in ripgrep, helps only someone who already suspects a gap. Stored on the item, it reaches every output and `status` without another pass over the files.
- Files over `max_bytes` are indexed by name with a `partial` note instead of being left out of the plan, so a search for the file finds it and says why its text is missing. Files `exclude` leaves out are only counted with a few examples in the source's state: walking excluded folders (`node_modules`) to list them would cost what excluding them saves.
- Other memory systems come in through their export files (`memory-export`, one format per system), not their APIs or databases: an export is a documented, stable shape that needs no credentials or client packages, and reading a file keeps the source read-only. Only the text and what the file says about it (time, user, agent, ids) is kept; their vectors are dropped, since they come from another model and mixing models breaks ranking. Formats are those with a real file or list API (mem0 `get_all`, Letta Agent Files and passages, Zep/Graphiti edge lists) plus plain lines for assistants whose memory can only be copied (ChatGPT, Claude); mem0's platform "memory export" was left out because it is an LLM-shaped summary against a schema, not the memories.
- Structured data files (JSON array of objects, or an array under one key; JSON Lines; CSV/TSV with a header) are read by the `files` source as one item per record, for every file by the same rule with no per-file settings: the item text is the record's string, number and flag values as `nested.key: value` lines, the title the first of title/name/subject/item/product/summary/headline/description/label (any depth), else the first text value that is not a number or a date; the item time is the first date-like field (`*date*`, `*time*`, `*_at`), a whole day when it has no time of day. A file with fewer than two records, or any other JSON, stays one text item. The item key is the file plus a hash of the record's text, so inserting or reordering records re-embeds nothing else; when a wrapper holds several arrays of objects only the longest is read. The `markdown` source stays Markdown-only; data files in a notes folder need a `files` source with `extensions` over it.
- The passage cap in `chunks` (400 per item) is gone: `max_chars` is the one limit on text per item, so there is one setting to raise.

## Media

- Every source of files reads a file through `documents.py` (name and bytes in, segments out, bytes from a local path or a range-readable download), so a library on a server reads what a local folder reads; each source keeps only its listing and change detection. Seafile had grown its own reader, which skipped pictures, scanned pages and any extension not on a list.
- A file indexed by name only records why in `info.unread` (format, too big, password, private key, switched off, missing extra, undecodable, no text, a recording on a server) as it is read; `status` counts items with no passage or media of their own straight from the index and groups them by that reason, so the count can't drift from what search can find. Items read before reasons were kept count as "unrecorded".
- How files are read has a version per family of files (`documents.READERS`: Markdown, text, PDF, pictures, legacy Office, iWork, records and the rest, by file name), kept on each item (`info.reader`, through the source's `reader_of(key)`); an item read by another version is read again, reusing vectors and OCR results, so an upgrade that reads more needs no `--reload`. One number for every format made any reader change download and read every file of a server library again; per family, an OCR change re-reads only pictures and PDFs. Kept in the source's state at first, it was saved only after a complete run without failures, so one file that always fails made every poll read every file again, and an interrupted re-read started over.

- Audio and video are embedded by the model itself (EmbeddingGemma 2 hears and sees), not transcribed: no whisper, no transcript cache. A hit points at the file and moment; an agent that needs the words transcribes that window with its own tools. Which kinds a profile embeds is its `encoders` list; a text-only profile skips media.
- How media is cut follows DigUp (MIT): 30 s windows every 25 s at 16 kHz mono (the model ignores audio past 30 s, and the overlap keeps a sentence whole), windows under about -50 dBFS skipped; a frame every 3 s (fewer past 1,200), one kept per shot by an 8x8 average hash within 4 bits, scaled to the model's 70-token budget so a frame costs seconds, not a minute. Frame times come from ffmpeg's `showinfo`, not from counting, since `fps` filters shift by a slot.
- Windows, frames and rendered pages are read lazily (`Segment.media` as a function, the hash from file fingerprint, place and settings), so a long recording never sits in memory and a re-read reuses every vector without decoding. At most `MEDIA_STEP` (30) media inputs per item per pass; the rest wait in `info.media_waiting` and are embedded after the source's other items, then by the next run.
- PDFs are read per page (`loc` = `page N`); a page under 200 characters of text is also rendered with pypdfium2 (Apache-2.0/BSD, the `pdf-scans` extra) at the 280-token budget and embedded as a picture, and rendered again at 2000 px for OCR. Without the extra the item records why its scans weren't read.
- Pictures and scanned pages get OCR as well as their image vector: the image vector finds a receipt or a form by what it looks like, but not by the name, number or Chinese phrase written on it, which keyword search needs as text.
- OCR is RapidOCR (Apache-2.0, code and models) running PaddleOCR's PP-OCRv6 small models in ONNX Runtime (MIT), the `ocr` extra. Measured on this project's CJK and Latin fixtures and real document photos on a 4-core CPU: PP-OCRv6 small read Simplified and Traditional Chinese, Japanese and English correctly at 2–7 s a picture and ~750 MB peak; PP-OCRv5 mobile read the same with worse line grouping; PP-OCRv6 medium took 17–55 s and 1.3 GB. Tesseract reads Chinese photos markedly worse and needs system packages; EasyOCR and Surya need PyTorch (and Surya's licence restricts use); VLM OCR (PaddleOCR-VL, DeepSeek-OCR) is too heavy for a CPU laptop.
- No PaddleOCR model reads Korean together with Chinese, so lines are found by the detector, each read by PP-OCRv6, and a line read with confidence under 0.8 is read again by PP-OCRv5's Korean model; the surer reading wins. Only unsure lines pay for the second model. RapidOCR's own pipeline drops lines its reader returns empty, which is how Hangul comes out of the Chinese model, so the lines are cropped and read one by one.
- OCR text is cached in `ocr-cache.db` in the data folder by file fingerprint and place (and the OCR version), so a reload, a model switch or a second media pass over a long scan doesn't OCR a page twice. The engines load on first use and are freed after each source's run, since they hold a few hundred MB.
- pypdf comes with its `crypto` extra (`cryptography`, Apache-2.0/BSD) in the core: PDFs AES-encrypted with an empty open password are ordinary (fillable forms), and without it pypdf can't read them at all.
- A PDF that needs a password to open is indexed by name with a `partial` entry giving the reason and no `setting` (no setting lifts it), like a file over a size limit: found by name, read again only when it changes.
- pypdf's warnings about repairs to malformed PDFs are kept below its log level: they say what pypdf fixed, not what rummage missed, and printed on stderr they turned `index -q` runs (which print only problems) noisy for ordinary PDFs.
- RTF, EPUB and .eml are read with the standard library only (an RTF tokenizer that skips font, style and picture groups; the EPUB spine; `email` with attachments through the same readers).
- The older binary Office formats are read in `legacy_office.py` with olefile (BSD) for the compound file: Word text from the piece table ([MS-DOC]) and PowerPoint text from its text atoms ([MS-PPT]), each a few dozen lines; Excel through xlrd (BSD), which reads only `.xls` now and is kept up for that. antiword and catdoc are GPL and unmaintained, textract shells out to them, Apache Tika and LibreOffice need a JVM or a 300 MB office suite. Encryption is read from the file's own flags (FIB `fEncrypted`, a FILEPASS record, PowerPoint's `EncryptedSummary` stream), and such a file is kept by name with the reason.
- Pages, Keynote and Numbers files are read in `iwork.py` with the standard library: an `.iwa` archive is Snappy blocks of protobuf messages, and text sits in two message types (text storages 2001/2005 field 3, table string lists 6005), so a Snappy decoder and a schema-less protobuf walk suffice; keynote-parser and numbers-parser need the full generated schemas and protobuf. Theme master slides are skipped (placeholder text). Files from iWork '09 are read through their Quick Look PDF.
- Jupyter notebooks are read as their cells and text outputs (streams, plain-text results, errors), not as JSON: the JSON's base64 pictures and metadata are noise to both indexes.
- Keys, certificates, password stores, `.env`, `.netrc` and folders like `.ssh` are never read, by name (DigUp's list), nor a text file holding a private key block; counted under `left_out` with `read_secret_files` to allow them.
- `.key` is not on that list: Keynote decks use it too, and were left out of the index entirely. A key file named `.key` is a text file holding a private key block (or binary), so it is still never read, only found by name.
- A file of a container format (zip for Office, iWork and EPUB; OLE for the older Office files) whose first bytes don't match is read by its content like any other file: a `.key` key file, RTF saved as `.doc`, a `.docx` that isn't one (then "damaged").

## Agent histories and live chats

- Sessions kept as append-only JSONL are read from where the last read stopped, restarting at the last turn's first line, so a growing reply is re-read but nothing older; a file that shrank is read again from the start. Gemini CLI's logs patch earlier records, so they are replayed whole when they change.
- Codex turns come from its `event_msg` user and agent messages, the text its UI shows, rather than the raw response items with their tool plumbing.
- Credentials are masked when printed, not when indexed: masking at index time would lose a value the user may later ask for, and the index is a local file kept mode 600. The patterns are well-known token shapes plus credential-like assignments; scanners such as gitleaks and detect-secrets are built for files and repositories, and a short pattern list is enough for masking result text.
- Masking is counted where it happens (`mask_count`) and each printed result carries `masked`, rather than counting `[secret]` in the output: a text that contains the marker itself would be miscounted, and per-result counts survive token budgets.
- Reading and embedding are separate phases with separate locks, so keyword search covers new items within seconds while vectors follow; pending vectors are stored with their model input, so any later run finishes them.
- Copies of one mail are recognised by Message-ID with no time window (a copy moved to an archive months later is the same mail) and collapsed at search time like chat messages, so both folders stay indexed.
- A client's notices before a person's words count as scaffolding only when the message starts with a bracketed notice line; the `> ` lines, a parenthesized line right under them and blank lines after it go with it. A message the person starts with their own quote stays as written.
- The quoted part of a reply is a passage of its own (the quote, then the reply's words), for every chat source and language: a reply is often searched for by what it answered, but sharing one vector with a long quote would make a short answer match only the quote. The reply's own passage stays the person's words.
- Recall searches with a prompt's pictures through the query daemon, not inline: a picture is cheap to embed only at the model's smallest image budget (70 tokens; measured on this 4-core machine: 22 s full size, 14 s at 280 tokens, 5.7 s at 140, 3.1 s at 70 on one thread, 1.7 s on two, 1.2 s on three; the vector at 70 tokens has cosine 0.89-0.91 with the full-size one's), so the daemon has a second llama-server with the image encoder for pictures, started on the first and kept, which a text query never waits behind; it embeds with up to three threads (`picture_query_threads`) at normal priority, a longer burst than a text query that niced background work gives way to, and holds about 1 GB while it is loaded (the daemon exits after its idle minutes). Measured on that machine while a backfill ran: a recall for words only took 0.5 s; with a new picture 1.7 s warm, 0.5 s for a picture the daemon had already embedded, and a first picture after the daemon started took over the 2 s deadline (the cue came with the next one). The hook asks it in a thread beside the text search and waits only until `--picture-wait` (2 s from the start of recall); a picture not ready adds no cue, and the daemon keeps its vector by hash so the next ask finds it. Only picture vectors are compared: a picture's vector and a passage's words sit far apart even when they are about the same thing, so a text passage would only add noise (the cues are pictures in chats, files and mail, each pointing at its item), and a match must stand out as `MIN_Z` (6) among the picture vectors: among 2,900 pictures in a real index, unrelated ones reach z 3-4 and related pages of the same app 4-5, while copies and the same page sit at 6-11.
- A message counts by how it reached the conversation, not by one event name: DSH messages come from message events and from the messages an inbox splice inserts (deduplicated by message id, the message event winning), Claude Code's from user records and queued-command attachments. DSH's title-request events carry user-role messages too, so a bare user-role shape isn't enough.
- A picture sent with a chat message is part of that message's item, not an item of its own: the image vector and the OCR passages are segments at `image N` of the turn (`chat_images.py`, through `documents.picture_segments`, the path files use), so a hit on a picture opens the turn it came with (`get --around`) and one id names the message. The OCR cache key and the vector hash come from the picture's content hash, not the turn's fingerprint, so a turn that grows with its reply is read again without reading or embedding its pictures again; the fingerprint of a turn with pictures holds their ids and the picture reader version, so a newer OCR reads only those turns again. The OCR passages start with `[picture N]` since `get` stitches a turn's text passages into one text. A picture that can't be read (its file is gone, over `limits.image`, ffmpeg can't decode it) is a `partial` entry of the turn and the words stay indexed; the turn isn't marked `unread`, which is for files kept by name only.
- `dsh-sessions` reads a picture from DSH's content-addressed attachment store (`attachments/v1/objects/<sha256[:2]>/<sha256>`, the bytes DSH normalized to PNG, JPEG or WebP), named by the `attachmentId` of the message's image block. Only messages a person sent are turns, so the pictures an agent or the assistant posted are not read; a sticker a person sent is a picture like any other. Hermes histories keep only a text description of a picture (its bytes were in the agent's own cache), already indexed as the message's text; Claude Code, Codex and OpenCode logs inline pictures as base64 and aren't read yet (`docs/queue.md`).
- Hermes's transcript files are read beside its database, not as a source of their own: they mostly repeat it and each other (a background review session replays the whole chat it reviews, under a new id), so a file turn is kept only when no database turn and no earlier file turn has the same message and start of answer (later answer steps are recorded differently in the two), and a message without an answer only when its words were sent nowhere else; an excluded session's turns count as seen, so a replay of it stays out. Deduplicating by session id would have kept every replay, and keeping all for search-time collapsing would have stored each chat several times. The files are re-read whole when their count, size or newest time changes, since the comparison needs all of them; the folder is opt-in because a live Hermes keeps everything in its database.
- A source that reads its data differently declares a new `reader`; a saved state from another reader is dropped, so the next run plans everything again and re-reads only items whose fingerprint changed, instead of asking for `--reload`.
- The same chat message in two sources is recognised by its text with leading bracketed notices removed (sender tags, channel headers that one recorder adds and the other doesn't) and times within 10 minutes, and collapsed at search time rather than dropped at index time: both records stay, so either source can be switched off without losing the message.
- Agent histories found on the machine are listed by `rummage setup` with the command to switch each on and asked about one by one at a terminal, never switched on unasked; switching one on prints how to switch it off.
- Recall's recent part adds turns from other sessions only when they hold 30% of the prompt's words (`SHARED_WORDS`, the bar a weak meaning match needs). At "any word in common", a day of hook recalls on a live home got 36% of its leads from there, nearly all the person's own messages in other chats sharing one or two common words (CJK pairs like "what" or "a bit"); replayed, 560 of 577 fall below the bar.
- Recall keeps a day of what it showed which chat session (`recalled.jsonl` in the data folder, outside the index so a hook never waits on an index run's write lock; recalls without a session aren't recorded). An item shown to the same session in the last 6 hours is left out, since the agent still has that block: in the same day a third of all leads repeated one already shown to that session, one item 16 times. An item shown to 3 or more other sessions in the last day is treated as a hub and counts only by its words, not its meaning: an OCR'd chat log in Chinese sat near every casual Chinese prompt (z 3.1-4.8) and came back 17 times in a day for unrelated prompts. This is a count-based form of querybank normalisation (Bogolin et al., CVPR 2022: past queries tame items that are near everything), without storing query vectors. Replayed on that day: 1,611 leads became 831, leads from items shown 5 or more times 491 to 0, the chat log 17 to 3. Raising its meaning bar instead would hit every passage of that kind, and a per-item hubness score needs query vectors kept around.
- A short prompt (under 12 content words) is searched by meaning with the turn before it, from the hook or the index (the last 600 bytes of the session's newest turn), and its own words only back a meaning match: replies like "rename it then" or "not the others" recalled noise from their few words, while the answer sat in the turn they replied to. Its words still drive keyword search, since the turn's words would swamp them.
- What recall embeds is sized to a hook's time: a vector's time grows with its tokens, a hook has a few seconds, and on a 4-core machine with three cores taken by normal-priority work, a 2,000-character prompt plus 1,000 characters of the turn before took 4 s at the median. A long prompt gives its start and end, 1,200 bytes of UTF-8 in all; bytes stand in for tokens across scripts (EmbeddingGemma: 0.8 tokens per CJK character, 0.3 per Latin one). On the query daemon's one thread (see Runtime) that is about a second, idle or busy. The turn before a follow-up gives its last 600 bytes. Measured on 49 long and 60 follow-up real prompts against the old text, judged blind: the follow-ups' picks were as good (5 better, 5 worse, 6 even of 16 that differed), while a long prompt cut to 600 bytes lost (1 better, 7 worse, 4 even of 12), so a long prompt gets twice that. Words are still matched against the prompt's start and end up to `--max-query-chars`, so a question after a pasted text is found by its words too (mem0 issue 7835 shows the same paste-then-question shape). Embedding a summary or keywords instead would need a model call or a guess inside the hook's budget; late chunking is for passages, not queries.
- A recall meaning match within a sixth of the gate (3.0-3.5 for EmbeddingGemma 2) needs 30% of the query's words as well. Picked from replayed recall blocks: the unrelated passages sat there sharing few words; the useful ones stood higher or shared a third.
- The session's own turns from the recent window are left out of recall: the agent has them, and the prompt being answered could match itself once read.
- The note on an unfinished index goes into a recall block only when it changes how to read the results (a result's source is mid-read, a tenth of passages lack vectors, the last run stopped or failed); repeated on every prompt through a two-hour re-read, it was noise.
- Harness adapters only carry recall's block to the model; every rule about what to recall stays in `rummage recall`. One plugin folder at the repository root serves Claude Code and Codex, since Codex reads Claude Code's marketplace, plugin manifest and `hooks/hooks.json` as they are. OpenCode keeps the block in the prompt's metadata and adds it in the request hook, so the text the user typed is stored unchanged while each request still carries the same block for that message.

## Scopes

- One index, filtered per query by the folder it runs in, instead of an index per project: what a project sees is its own files and its chats, and an assistant's home sees everything, which is mem0's one store with `user_id`/`agent_id`/`run_id` filters rather than Letta's or DigUp's separate stores; a separate code index (DigUp) would need its own model run, ranking scale and status. Filtering is in SQL on the item's source, ref and recorded working folder, so it costs nothing at index time.
- A project is the git repository holding the folder, worktrees included, as Claude Code keys its auto memory (`~/.claude/projects/<repo>/memory`); repository files are found by reading `.git` files, not by running git, so the per-prompt check stays a few file reads.
- A git repository is a project scope only once a source reads files in it; until then a query there falls through to the default scope and says how to add it, because a scope of nothing returned empty results for every search run inside an unread repository.
- The deepest matching folder wins, and a configured scope beats a project at the same depth: the nearest context is the most specific one, as CLAUDE.md files closer to the working folder are read last. `local` sources are seen only from inside their root, as DigUp keeps code out of other searches.
- New projects are added to the config file rather than a separate registry: the config is what every command reads anyway, so a project source is an ordinary source to list, switch off or drop.
- Project files are what `git ls-files -co --exclude-standard` lists, so `.gitignore` decides; key and password file names are skipped on top of the default dot-file exclude.
- A file is text by its content (no NUL in the first 8 KB, valid UTF-8), not by an extension list, for every source of files: an extension list kept missing source code and build files, which were then found by name only. Remote files are sniffed with one range request for their first 8 KB.
- A paused index skips what is in reach and doesn't save the source's read position, so the next run after the pause reads it again; nothing new is stored about it. A private pause or `exclude` is a mark checked against each item before it is read and against the index when added; removing a mark resets the sources' read positions, and items already kept are skipped by their fingerprints.
- Pauses and marks are one JSON file in the data folder, so the prompt hook checks them with one read and no database.
- `project ensure` starts `rummage watch` rather than a one-off index run: one process keeps every source current, it restarts itself when the config changes, and a lock keeps it to one per data folder.
- A watch `project ensure` starts runs `--on-demand` and gives way: one started any other way (service, supervisor, by hand) waits for the lock instead of exiting, and stops an on-demand holder named in `watch.holder` (pid, on demand or not) with SIGTERM, which is TerminateProcess on Windows. A supervisor only restarts the process it started, so a supervised watch that exited 0 on a busy lock left an auto-started one indexing outside supervision. The supervised side waits rather than the hook checking for a configured service, because supervisors are many (systemd, launchd, Task Scheduler, an agent harness's watchers) and only the process knows how it was started; watchman (spawning through launchd when its plist is installed) and gpg-agent (`--supervised`, `no-autostart`) solve the same split from the client side, which needs one check per supervisor. A watch stopped by SIGTERM stops its vector maker and its reading run with it.

## Storage

- SQLite stays the only backend: one file, no server, exact vector scans are fast at personal scale. The seam is `Store` (no SQL anywhere else), and `rummage.export.v2` is the way between engines, so a second backend can come without a migration tool of its own.
- The export keeps vectors as raw little-endian float16 rows next to JSONL text, rather than one JSON or a database dump: any language reads it, vectors stay exact, and the vector version in the manifest stops mixing models.
- `rummage service` writes the OS's own supervisor config (systemd user unit, launchd agent, logon task) instead of shipping a supervisor: restarts and login start come from the system people already use.

## Runtime

- A search with no daemon starts one (`daemon.ensure`) and waits for its answer rather than also loading the model itself: one model load instead of two in memory, about the same wait.
- The daemon also holds the active model's vectors in memory and scores each query against them; the search then reads only each segment's item, kind and script, through a covering index (`segments_meta`). Reading every vector from the index file is fast while the file is cached, but on a small machine under memory pressure the file drops out of the page cache, and the 40 MB of a 40,000-vector index then took 1.3 s cold (0.07 s warm) against 0.11 s for the covering index, which made prompt-time recall miss its 3 s budget. The snapshot is read again at most once a minute while the index changes (SQLite `data_version`), in the background, so a search during a long backfill may miss vectors made in the last minute; their passages are still found by words. Without a daemon, searches read the vectors themselves as before. The daemon holds a per-data-directory lock for its life, so searches racing to start it end up with one; it exits after `[daemon] idle_minutes` unused so memory comes back. A prompt hook starts it without waiting, since hooks must stay fast.
- The GPU is used only when `rummage setup` measures it (adapted from DigUp): the platform's GPU build must see a device, embed a fixed sample in at most 0.8 of the CPU build's time, and give the profile's reference vectors (cosine ≥ 0.999); otherwise the CPU build stays, and the reason is kept in `runtime/backend.json` for `status`. Each GPU the build lists is timed on its own and the fastest agreeing one is pinned with `--device` (llama.cpp otherwise splits layers across every GPU, an integrated one included). The check reruns when the pinned llama.cpp build changes.
- Vulkan, not CUDA, on Linux and Windows: one 30–40 MB build runs on NVIDIA, AMD and Intel GPUs through their normal drivers, while the CUDA builds need a matching CUDA runtime (another 400+ MB download) for a 300M-parameter embedding model whose speed is bound by small batches anyway. macOS builds already contain Metal, so there the check only compares `-ngl 999` with `-ngl 0`. Every embedder passes `-ngl` explicitly, so the CPU choice really is the CPU.
- Background work has one thread budget, `[runtime] background_threads` (cores - 1 by default), so a re-read on a small machine leaves a core to the query daemon, which isn't counted and keeps normal priority. Queries (the daemon's model, and a search that loads the model itself) get one thread at normal priority, not `threads`: niced background work yields to it, and llama.cpp's threads wait for each other at every layer, so with more threads a query is only as fast as the thread whose core other normal-priority work holds. Measured on a 4-core machine (EmbeddingGemma 2, 600/1,200/2,400 bytes): idle, one thread took 0.47/0.94/2.15 s, two 0.27/0.52/1.24 s, four 0.42/0.98/1.23 s; with three cores busy at normal priority, one thread 0.51/1.01/2.54 s, two 0.41/1.23/1.95 s, four 2.15/2.11/3.63 s. Thirty hook recalls (`recall --hook`, real prompt shapes, long ones cut to 1,200 bytes) with two or three cores busy: one thread never passed 2.6 s in 90 recalls, two threads passed 3 s three times in 90. One thread costs a tenth of a second at the median on an idle machine and makes a query's time independent of the load, which is what a hook's budget needs. 0.25.3 gave queries every core and 0.25.5 had the daemon read busy cores from `/proc/stat` every 10 s and swap in a server with the free count, sizing recall's text to it; that worked only on Linux, restarted servers as the load moved, and is gone. A watch runs a reading run and a vector-making run at once, so the budget is split: the vector maker gets `threads` (and grows to `max_threads` only on idle cores, within the budget), the reading run the rest; inside a reading run OCR and the picture embedder take turns, so both get that whole share. Per-part knobs (`ocr_threads` in 0.22.0) let the parts add up past the cores, which on a 4-core machine left nothing for searches. OCR's threads are set for ONNX Runtime and OpenCV, which otherwise take every core. ONNX Runtime's idle workers are set to sleep rather than spin (RapidOCR has no setting for it, so `ocr.py` extends the session options where RapidOCR builds them): each model has its own pool, and the spinning pools made a 2-thread reading run use close to 3 cores.
- An `index` run that finds another run reading (a watch's, a scheduled one) stops without making vectors: the run that is reading makes them, and a second embedder beside it only competes with it and with searches for the same cores. Asked to `--wait`, it reports busy as before.
- While `rummage watch` runs for a data folder, an `index` it didn't start (a scheduled backstop, a manual run) does nothing and says so: the watch reads changes as they come and re-plans every source on its interval, and between its batches no lock of its own runs is held, so the reading lock alone let a second run start its own embedder and OCR beside the watch's vector maker. The watch marks its own runs through the environment (`RUMMAGE_WATCH_RUN`) and holds its lock for its life, so a dead watch never blocks an `index`.
- Threads follow the load by restarting `llama-server` (about a second) when the wanted count changes, checked at most once a minute: llama.cpp fixes the thread count at start, and a minute-scale check matches the 1-minute load average it reads.
- An accelerator is trusted by result, not by name: it is used only when its vectors for three fixed reference texts agree with the profile's published ones or those stored at the first run (cosine ≥ 0.999, the same bar `doctor` applies to a llama.cpp upgrade). Queries keep using the local model or daemon, so search never depends on another machine unless the model itself is remote.

## OCR on another machine

- Pictures are prepared (decoded, transparency flattened, long side cut to 2,000 px) on the machine that reads, then sent as JPEG quality 95 to `ocr-serve`, which only finds and reads the lines. The cache key and the text stay on the reading machine, so a server holds no state and any machine with the `ocr` extra can be one; the server's reader version must equal the client's or the item fails, so a mixed pair never fills the cache with other models' text.
- No fallback to local OCR when the server is gone: a run that silently went back to the slow local reader would be the same run the server was set up to avoid, so the item fails (the run goes on, the item is read again next time).
- Several pictures go at once only to a server (`PARALLEL` threads here, `--workers` there, each worker with its own engines): rendering a PDF page stays one at a time under a lock, since the renderer isn't safe from two threads.
- A remote embedder is retried for about 30 seconds and then given up on for the run, not failed: a missing vector only means a passage waits and is made by the next run, whereas a failed run turns the index card red for a restart. There is no local fallback mid-run either (a local embedder would start on the busy machine); the accelerator is judged once at the start of a run.

## Feedback

- A `get` of a result soon after the search that showed it is the only signal recorded: it needs no extra step from people or agents, and it says which result was the useful one. The boost is small and capped (0.4 per open, two at most) and needs half of the query's words in common, so one open can't take over unrelated searches. The last search lives in a small file next to the index, not in it, so searching stays read-only.

## Time in queries

- `--since/--until` match an item's own time or the period its path names (`weekly/2026-W44.md` is about that week), as a filter. A dated note is often edited long after the period it covers, so its change time alone would put it in the wrong window.
